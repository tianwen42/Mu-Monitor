# Mu-Monitor 工业级开发 Todolist

> 目标：把当前 Qt 界面原型逐步演进为一个可在小型工业现场试运行的 Windows 设备监控终端。
>
> 当前建议规模：单机部署、1 到 20 台设备、TCP 自定义协议、SQLite 本地存储。
>
> 工作原则：一次只完成一个可验证的小任务；先保证正确性和可恢复性，再增加协议和功能。
>
> 2026-10-15 是目标演示日期，不是硬截止日期；学习质量优先，具体安排见 [DELIVERY_PLAN.md](DELIVERY_PLAN.md)。
>
> 配套技术学习路线见 [LEARNING_PATH.md](LEARNING_PATH.md)。
>
> 当前学习进度见 [LEARNING_PROGRESS.md](LEARNING_PROGRESS.md)。

## 一、真实工业项目关注什么

工业监控软件和普通课程项目最大的区别，不是界面更复杂，而是异常发生时仍然要可解释、可恢复、可追踪。

本项目按照以下质量标准推进：

- 采集数据不能静默丢失；写入失败必须告警并留下日志。
- 网络断开、设备离线、重复帧、坏帧和数据库繁忙都属于正常异常场景。
- 连接、采集、告警和数据存储必须有明确状态，不能只靠界面按钮猜测。
- UI 线程不能直接承担高频网络解析、数据库写入和大批量导出的工作。
- 配置、数据库结构和协议都必须有版本，升级时不能随意破坏旧数据。
- 所有告警都要能够流转和审计，不能只停留在 `QListWidget` 中。
- 程序必须支持长时间运行，并能够在发布前完成 8 小时和 24 小时稳定性测试。
- 能测试的逻辑要和 Qt Widgets 解耦，关键模块必须有自动化测试。
- 不为了“看起来高级”引入微服务、云平台、消息队列集群等超出项目规模的技术。

## 二、项目的工业适用边界

### 本项目适合

- 一台 Windows 工控机或办公电脑作为监控终端。
- 通过 TCP 采集少量设备的数据。
- 本地展示实时状态、趋势和历史数据。
- 产生、确认、恢复和查询告警。
- 使用 SQLite 保存中小规模历史数据。
- 后续选择性接入 Modbus TCP、MQTT 或串口设备。

### 本项目暂时不适合

- 多机房、多节点高可用系统。
- 数万设备的大规模并发采集。
- 严格实时控制和安全联锁。
- 直接控制可能造成人员伤害或重大设备损坏的执行机构。
- 未经确认就接入真实生产 PLC 的写寄存器操作。

如果未来要控制真实设备，需要单独进行风险评估、权限控制、命令确认、超时处理和现场联调。

- [ ] Debug 构建成功。

- [ ] README、协议文档或数据库文档同步更新。

```text

-> Debug 构建
-> 自动测试
-> Release 构建
-> 手工验收
-> 更新文档
-> Git 提交
-> 更新 Todolist
```

# 阶段 2：拆分 MainWindow

**目标：** 让 `MainWindow` 只负责界面，不再生成模拟数据、访问数据库或判断告警。

## 目标结构

```text
MainWindow
  -> AppController / MonitoringService
       -> IDeviceDataSource
            -> SimulationDataSource
            -> TcpDeviceDataSource
       -> TelemetryRepository
       -> AlarmEngine
```

## 任务

- [ ] 明确定义两种模拟能力：进程内 `SimulationDataSource` 用于 UI 和单元测试，独立 `DeviceSimulator.exe` 用于 TCP 和端到端测试。
- [ ] 定义 `IDeviceDataSource` 接口，包含启动、停止、状态信号和数据信号。
- [ ] 将模拟设备创建逻辑从 `MainWindow` 移到进程内 `SimulationDataSource`。
- [ ] 进程内 `SimulationDataSource` 不实现 TCP、粘包、CRC 或自动重连。
- [ ] `DeviceSimulator.exe` 不链接主程序的 `DatabaseManager`、UI 或业务对象。
- [ ] 将模拟数据的采样定时器移入 `SimulationDataSource`；`MonitoringService` 只管理启动、停止、状态和业务协调，不生成数据。
- [ ] 将设备在线、采集状态和历史点缓存从 `MainWindow` 移出。
- [ ] 创建 `AppController` 负责装配服务、协调命令和向 UI 转发状态。
- [ ] `MainWindow` 只订阅 `AppController` 的信号。
- [ ] `MainWindow` 中不再直接调用 `DatabaseManager`。
- [ ] `MainWindow` 中不再使用 `QRandomGenerator` 生成模拟业务数据。
- [ ] 为 `SimulationDataSource` 编写确定性测试，随机种子必须可配置。
- [ ] 为启停、重复启停、离线设备和停止采集编写测试。

## 完成标准

- [ ] `mainwindow.cpp` 明显缩短，只保留 UI 初始化和展示逻辑。
- [ ] 更换数据源时不需要修改表格、趋势图或告警控件。
- [ ] 没有 Widget 直接包含 `DatabaseManager.h`。
- [ ] 模拟数据源可以脱离主窗口独立测试。

# 阶段 3：设备模拟、协议 v1 和共享协议库

**目标：** 建立可独立运行的设备生产者程序，冻结二进制协议，并让模拟器和客户端复用同一套编解码实现。

- [ ] 进程内 `SimulationDataSource` 只负责本进程内的确定性模拟数据。
- [ ] 独立 `DeviceSimulator.exe` 负责真实 TCP、断线、重连和故障注入。
- [ ] 两种模拟能力不能共享主程序内部对象。
- [ ] 测试文档必须明确每个测试应该使用哪一种模拟能力。

## 3.2 独立设备生产者程序

- [x] 保留并独立构建现有 `DeviceSimulator` 目标。
- [x] 使用 `QTcpServer` 接受 Mu-Monitor 的 TCP 连接。
- [x] 显示客户端连接数量。
- [x] 支持高温、高压和离线基础场景测试。
- [ ] 模拟器支持配置监听地址、端口、设备数量和发送周期。
- [ ] 默认模拟 10 台设备，每秒发送一次遥测和心跳。
- [ ] 模拟器显示发送帧数、发送速率、连接数和错误数。
- [ ] 支持固定随机种子，保证测试结果可重复。
- [ ] 支持手动触发高温、高压、离线、延迟、主动断开和重复帧。
- [ ] 支持注入坏 CRC，用于验证客户端错误隔离。
- [ ] 支持一键断开所有客户端，用于验证自动重连。
- [ ] 客户端断开后模拟器继续运行，不产生崩溃或状态污染。
- [ ] `DeviceSimulator.exe` 可以独立启动、关闭和重复运行。
- [ ] `DeviceSimulator.exe` 不依赖主程序 SQLite、UI 或业务对象。
- [ ] 增加正常场景、异常场景和客户端重连的集成测试。

## 3.3 协议 v1

- [ ] 编写 `docs/protocol.md`。
- [ ] 定义固定帧头、版本、消息类型、长度、序号、设备 ID、时间戳、负载和 CRC16。
- [ ] 明确所有多字节字段使用网络字节序。
- [ ] 定义单帧最大长度和最小长度。
- [ ] 定义遥测消息和心跳消息的二进制负载。
- [ ] 定义协议版本不兼容时的处理方式。
- [ ] 定义序号回绕和重复序号处理规则。
- [ ] 为正常帧提供固定十六进制测试向量。
- [ ] 为 CRC16 增加标准测试向量。

## 3.4 共享协议库

- [ ] 新建 `mu_protocol` 静态库目标。
- [ ] 将 `Protocol`、`Frame`、`FrameCodec` 和 `Crc16` 放入 `src/protocol`。
- [ ] `Mu-Monitor` 链接 `mu_protocol`。
